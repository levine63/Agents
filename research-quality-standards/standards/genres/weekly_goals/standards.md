# Weekly Goals And Weekly Reporting Standards

Version: 0.1.0
Status: Draft
Last updated: 2026-05-13

## Scope

These standards apply to:

- weekly goals
- short-term work plans
- weekly reports
- progress updates
- similar task-tracking artifacts used for research, operations, teaching, or software workflows

The goal is not bureaucratic compliance. The goal is:

- fast detection of blockers
- visible progress
- reproducibility of work
- institutional memory
- concise actionable feedback

Avoid:

- compliance theater
- excessive verbosity
- giant rewrites
- overengineering

## Core definitions

### Artifact rule

A task is done only if:

- it produced something another person can open and use
- and the artifact, link, file reference, or clear location is provided

Examples of acceptable artifacts:

- document
- table
- dataset
- code file
- pull request
- memo
- figure
- synthesis note
- cleaning log
- issue log

Bad:

- `Worked on literature review`

Good:

- `Drafted two-page synthesis of 12 papers and saved summary table in project folder`

### Carried over

A task is carried over if:

- it was listed as planned in the previous period
- and it is still not complete in the current period

Carried-over work is not a problem by itself.

Unexplained carried-over work is a problem.

## What a good weekly-goal or weekly-report artifact should do

A good artifact should make it easy for another person to answer:

- what is the parent goal
- what concrete work is planned or completed
- what visible artifact should exist
- what is blocked
- who owns the next step

## General task expectations

Tasks should generally:

- have a parent goal
- produce a visible artifact
- have a definition of done
- be small enough for visible progress within the reporting window
- expose blockers clearly

Prefer decomposition into smaller concrete deliverables over large vague work items.

## Required content

At draft quality or above, a weekly goal or weekly report should make clear:

- the reporting period or planning period
- the owner or contributor
- the major goal or objective
- the task list or work units
- expected or delivered artifacts
- blockers, dependencies, or decisions needed
- next steps

## Weekly goal standards

A strong weekly goal should answer:

- what will exist by next week that does not exist now

### Recommended weekly-goal fields

A good weekly goal template should usually capture:

- name
- team
- week of
- parent team goal or subgoal
- current task ID when relevant
- weekly goal
- concrete deliverable by next meeting
- definition of done
- expected artifact type or link location
- estimated hours
- first step
- likely blocker
- help needed now
- confidence: `green`, `yellow`, or `red`

### The one-week test

A weekly goal is too large if:

- it may take several weeks
- it has many unclear parts
- it depends on a decision not yet made
- it has no visible artifact
- or completion cannot be judged at the next check-in

If a decision is not yet made, the weekly goal should often shift to unblocking that decision.

Examples:

- write a one-page options memo
- draft three clarifying questions
- produce a short meeting summary with a recommendation

### First-step expectation

The first step should be concrete enough to start quickly.

High-quality first steps usually take fifteen minutes or less.

If someone cannot name a small first step, they are often not ready to start.

### Confidence status

Use confidence honestly:

- `green`: clear path and likely to finish
- `yellow`: can begin, but a blocker may intervene
- `red`: meaningfully blocked or unclear

Hidden `red` is a management failure.

Do not write `green but ...`.

### Strong weekly-goal formula

A strong weekly goal should usually fit this sentence:

- `By next lab, I will produce [specific artifact] that helps [parent goal], and it will be done when [definition of done].`

## Weekly report standards

Weekly reports should make completed work, unfinished work, blockers, and next-week commitments visible.

### Recommended weekly-report sections

At minimum, a strong weekly report should usually include:

1. outputs delivered
2. in-progress work
3. next-week plan
4. blockers, delays, and requests
5. time and output check
6. risks and mistakes
7. skill built
8. one thing the supervisor should know

### Outputs delivered

Completed work should be reported as outputs, not activity descriptions.

Each output should ideally include:

- task
- output produced
- evidence link or file reference
- time spent
- self-assessed quality when useful

If an output entry has no usable artifact reference, it should be flagged.

### In-progress work

In-progress items should usually include:

- task
- progress percent
- next concrete step
- blocker
- carried-over status

If a task is carried over, the report should explain why.

### Next-week plan

Next-week items should usually state:

- parent goal or subgoal when it is not already obvious from context
- task
- concrete deliverable
- definition of done
- deadline
- expected hours
- priority

Avoid vague verbs unless paired with a specific artifact and completion condition.

Next-week commitments should be feasible within one reporting cycle.

If a planned item is too large to finish within a week, it should usually be rewritten as a smaller deliverable.

### Blockers, delays, and requests

A good blocker note states:

- what is blocked
- why it matters
- what has already been tried, ideally with dates
- what is needed
- by when

`Waiting for response` without context is weak blocker reporting.

### Time and output check

Time reporting should help explain the week, not act as fake precision.

Helpful fields often include:

- hours worked
- planned versus actual hours
- outputs completed versus outputs planned

Large mismatches should be explained briefly.

### Risks and mistakes

Weekly reports should acknowledge:

- one risk
- one mistake, failed path, or pivot
- or, if truly none, the lowest-probability concern worth watching

## Goal and task quality

### Clear parent-goal linkage

Tasks should roll up to a larger objective rather than appearing as isolated chores.

If a task does not clearly support a larger objective, flag it for clarification.

### Visible artifact expectation

Each substantial task should point toward a visible artifact when possible.

Examples:

- updated code
- cleaned dataset
- memo
- table
- slide
- README revision
- literature note
- decision log entry

Purely process-oriented tasks are acceptable when necessary, but should still state the intended output or decision.

### Definition of done

Tasks should say what completion looks like.

Weak:

- `work on analysis`
- `continue literature review`

Stronger:

- `produce cleaned analytic file with documented exclusions`
- `draft one-page literature synthesis with five papers and open questions`

For weekly reports, the next-week plan should also make `done` visible rather than relying on vague intent.

### Appropriate granularity

Tasks should be small enough to show visible progress and large enough to matter.

Flag:

- oversized tasks that hide many subproblems
- repeated carryover tasks with no visible movement
- tiny tasks that create noise without advancing the goal

## Blockers and dependencies

Blockers should be explicit, not implied.

Good blocker reporting states:

- what is blocked
- why it is blocked
- what dependency or decision is missing
- who can unblock it when known

Repeated `in progress` status without blocker explanation is a warning sign.

## Ownership and accountability

Ownership should be clear enough that a reviewer can tell:

- who is responsible for the next action
- whether the task needs handoff
- whether the task depends on another person or team

Unclear ownership is a quality problem even when the task description is otherwise clear.

## Progress reporting quality

Progress updates should distinguish between:

- work completed
- work started but not finished
- work deferred
- work blocked

Do not treat mere effort or time spent as progress unless it produced a meaningful intermediate result.

## Weak phrases to flag

Flag vague goal or report language such as:

- `work on`
- `continue`
- `help with`
- `research`
- `look into`
- `make progress on`
- `think about`
- `started`
- `worked on`

These phrases are not automatically wrong in private notes, but they are weak in weekly goals and output reporting unless paired with a specific artifact and completion condition.

## Common failure modes

Flag:

- vague tasks
- oversized tasks
- repeated `in progress` tasks
- missing artifacts
- unclear ownership
- missing deadlines or reporting period
- hidden blockers
- tasks that do not roll up to any meaningful goal
- goals lists that are too long to be reviewable
- missing evidence for claimed completed outputs
- carried-over work with no explanation
- hours and outputs that do not plausibly fit together with no explanation
- `green` confidence hiding obvious blockers

## Reviewer stance

The reviewer should prefer:

- smaller concrete deliverables
- explicit blockers
- visible artifacts
- concise repair suggestions

The reviewer should not demand corporate-style status theater or overly polished prose.
