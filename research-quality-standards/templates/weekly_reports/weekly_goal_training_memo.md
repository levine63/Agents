# How To Set A Good Weekly Goal

## Why weekly goals matter

Weekly goals turn large, vague projects into visible progress.

Most research tasks fail not because people are lazy, but because the task is too broad, unclear, or missing a definition of done.

A good weekly goal should answer:

- what will exist by next week that does not exist now

## Basic rule

Do not write an activity. Write a deliverable.

| Weak activity | Strong deliverable |
|---|---|
| Work on literature review | Add 10 papers to the evidence table |
| Help with coding | Write and test the missingness validator |
| Think about survey questions | Draft 8 revised questions with comments |
| Clean data | Produce duplicate-check table and cleaning log |
| Read background materials | Write a 1-page summary of 3 closest papers |

## The one-week test

A weekly goal is too large if:

- it may take several weeks
- it has many unclear parts
- it depends on decisions not yet made
- it has no artifact
- you cannot tell when it is done

If so, shrink it.

Better:

- `Draft the first 2 columns of the literature matrix for 8 papers.`

Not:

- `Finish literature review.`

## Definition of done

Every weekly goal needs a definition of done.

Bad:

- `Make progress on analysis.`

Good:

- `Run the baseline balance table for age, gender, education, and baseline outcome; save Stata log and draft table.`

## Artifact rule

Most weekly goals should produce an artifact:

- document
- spreadsheet
- table
- figure
- code file
- pull request
- cleaned dataset
- memo
- protocol
- survey draft
- annotated bibliography

If there is no artifact, explain how progress will be verified.

## Ambiguity rule

If a decision is not yet made, your goal is not to `do the task`.

Your goal is to unblock the decision.

Examples:

- write a one-page options memo
- prepare three clarifying questions
- produce a short meeting summary with recommendation

## First-step rule

Your first step should usually take fifteen minutes or less.

If you cannot name a small first step, the goal is probably still too vague.

## Blockers

A blocker is not an excuse. It is useful information.

Good blockers include:

- `I need access to the dataset.`
- `I need clarification on which outcome definition to use.`
- `I do not know whether to cluster standard errors.`
- `I need feedback on the survey draft.`

Report blockers early. Do not wait until next lab if you are stuck.

## Confidence

| Status | Meaning |
|---|---|
| Green | I know what to do and expect to finish |
| Yellow | I can start, but something may block me |
| Red | I am stuck or need clarification before meaningful progress |

Red is not failure.

Hidden red is failure.

Do not write `Green but ...`.

## Final standard

A strong weekly goal should fit this sentence:

- `By next lab, I will produce [specific artifact] that helps [parent goal], and it will be done when [definition of done].`
